# CI (Lint + Tests) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a GitHub Actions workflow that runs `ruff check .` and `pytest` on every push/PR, with a genuinely clean starting point (not an assumed one) and a working public GitHub remote.

**Architecture:** Three small, independently reviewable tasks — (1) make the existing codebase pass a scoped ruff ruleset, (2) add the workflow file itself, (3) update README documentation (badge, stale status banner, roadmap). The GitHub repo creation, push, and live-workflow verification are **not** implementation tasks in this plan — they're a distinct, controller-executed final phase (see "After This Plan" at the end), because they're one-time, hard-to-reverse, real-world side effects (a new public repo, the entire commit history becoming publicly visible) that must not be delegated to an isolated subagent without the full authorization context negotiated during design.

**Tech Stack:** ruff (new dev dependency), GitHub Actions (`actions/checkout@v4`, `actions/setup-python@v5`).

## Global Constraints

- **Ruff ruleset, exact:** `select = ["E", "F", "I"]`, `ignore = ["E501"]`, `target-version = "py311"` in `pyproject.toml`'s `[tool.ruff]`/`[tool.ruff.lint]` sections — do not add other rule categories or change the line-length ignore. This was chosen empirically (see design doc §2) specifically because this codebase's narrative-comment style was never held to an 88-char limit; do not "fix" long lines as part of this plan.
- **No reflowing/reformatting beyond the 27 pre-identified ruff findings.** The 27 findings (23 unsorted-import blocks, 2 unused imports, 2 mid-file imports in one file) are the complete, exact list verified against the real codebase before this plan was written — see Task 1. Do not run a broader formatter (black, `ruff format`) or touch any file not in that list.
- **Python version: 3.11 only, no matrix.** Matches `pyproject.toml`'s `requires-python = ">=3.11"` floor exactly.
- **Workflow triggers on `[push, pull_request]`**, any branch — matches the architecture doc's "every push/PR" requirement verbatim.
- **No secrets, no permissions blocks, no caching** in the workflow — none are needed (see design doc §4) and none should be added speculatively.
- **`pull_corpus.py` DOES have partial test coverage** (`_fetch_paginated` dedup logic, `tests/test_pull_corpus.py`) — when any task's text discusses which scripts are tested/untested, this exception must be stated accurately, not glossed over (this was a real inaccuracy caught and fixed in the design doc's review — see design doc §1).
- **Badge/repo URL:** `https://github.com/marshfalex/fda-device-rag` — the GitHub username was confirmed via `gh auth status` before this plan was written, not a placeholder.

### Task 2: CI workflow file

**Files:**
- Create: `.github/workflows/ci.yml`

**Interfaces:**
- Consumes: `pyproject.toml`'s `dev` extra (from Task 1 — must include `ruff` for `ruff check .` to succeed in CI).

No tests for this task in the traditional sense — a GitHub Actions workflow can't be unit-tested locally. It's verified by the controller's real push-and-watch step after this plan's tasks are merged (see "After This Plan"), not here.

- [ ] **Step 1: Create the workflow directory and file**

Create `.github/workflows/ci.yml`:

```yaml
name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install -e ".[dev]"
      - run: ruff check .
      - run: pytest
```

- [ ] **Step 2: Validate the YAML is well-formed**

Run: `.venv/Scripts/python.exe -c "import yaml; yaml.safe_load(open('.github/workflows/ci.yml')); print('valid YAML')"`

(If `pyyaml` isn't installed, run `.venv/Scripts/python.exe -m pip install pyyaml` first — this is a one-off local validation tool, not a project dependency, so do not add it to `pyproject.toml`.)

Expected: `valid YAML`

- [ ] **Step 3: Commit**

```bash
git add .github/workflows/ci.yml
git commit -m "feat: add GitHub Actions CI workflow (ruff + pytest)"
```

## After This Plan (controller-executed, not a delegated task)

Once all 3 tasks are individually reviewed and a final whole-branch review passes, the controller (not a subagent) performs these steps directly, with the user present:

1. `gh repo create fda-device-rag --public --source=. --remote=origin` (or equivalent — create the repo, add it as `origin`).
2. `git push -u origin master`.
3. `gh run watch` (or `gh run list` + `gh run view <id>`) to confirm the workflow actually runs green on this real push — not assumed from the workflow file's correctness alone.
4. Only after step 3 confirms green: update `README.md`'s status banner (drop "and CI are future phases") and flip the Roadmap table's Phase 5 row to `Done`, commit and push that final change.

This sequencing exists because a new public repo and a full-history push are the two most consequential, least reversible actions in this entire plan — they deserve direct execution and real verification, not delegation to an implementer subagent that has no context on the authorization already negotiated for this specific repo name and visibility.
